# Contributing to Langboard

Thanks for your interest in contributing! We welcome pull requests, issues, and feedback.

## Before You Start

- Make sure there's no open issue or PR that already addresses your change.
- If your change is significant, open an issue first to discuss your idea.
- Be respectful and follow our [Code of Conduct](CODE_OF_CONDUCT.md).

## How to Contribute

1. Fork the [Langboard GitHub repository](https://github.com/yamonco/langboard)
2. Create a new branch following [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow)
   - fix/...
   - feat/...
   - ...
3. Submit a pull request to the `main` branch with a clear title and description. Reference any issues fixed, for example `Fixes #1234`. Ensure your PR title follows the [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) format.
4. A maintainer will review your PR and may request changes.

## Development Environment Setup

For detailed instructions on setting up your local development environment, see [development guidelines](./DEVELOPMENT.md).

## Pull Request Checklist

- Run `make format`
- Run `make lint`
- Run `make unit_tests`
- Update relevant documentation when behavior or configuration changes

## Schema migrations and default data

Define schema changes in the shared model and `AppSchema` owners, then generate
the revision with the existing `db:migrate` command (`autogenerate=True`). Review
the generated operations and test upgrades from the preceding revision. Record
the generation command and baseline in the PR; a revision filename alone is not
evidence of generation. Keep applied revisions unchanged. Correct deployed
schema or data through a new reviewed revision rather than rewriting history.

Relationship display defaults belong in
`src/shared/py/langboard_shared/core/resources/locales/relationship_types.json`.
`RelationshipTypeBootstrap` inserts missing system semantics after database
upgrade, serializes concurrent startup transactions, and preserves existing IDs,
names, descriptions, activation choices, and edges. Keep new display text in the
resource owner and UI translations in the existing locale files. Do not add new
default-row seeds to schema revisions.

Revision `2c4e8a1f6b30`, introduced by commit `572c9154dad24adeb701f0e728e02c6d3aa7f611`,
predates that bootstrap ownership. Its generation command and baseline were not
recorded, so its schema operations must not be described as verified autogenerated
output. Its Korean default-row literals are frozen historical data, not the
source for new display defaults. Its exact legacy names `선행작업` / `후속작업`
identify the historical unclassified row without changing its ID or existing
edges. These historical literals and the migration regression's matching fixture
are the narrow tracked-source language exception; they do not permit Korean
display strings in new Python or TypeScript code. Existing installations retain
their saved names; bootstrap does not translate or overwrite administrator data.
