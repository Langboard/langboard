# 워크플로우 공통 트리거 계약

상태: 목표 설계. 현재 `entry_effects`, `entry_bots`, `policy_bots`, `continuous_effects` 구현을 이 계약으로 전환한다. 이 문서만으로 런타임 전환이 완료된 것은 아니다.

## 1. 기본 구조

워크플로우 규칙은 **언제 발생했는가(트리거), 현재 실행 조건을 충족하는가(조건), 무엇을 실행하는가(액션)**로 구성한다. 봇과 내장 효과(기존 화면의 스펠)는 액션 구현체다. 트리거와 실행 이력의 공통 모델에 봇 전용 필드를 두지 않는다.

기존 도메인 이벤트·예약 실행기·권한 검사·트랜잭션·발행 경로를 재사용한다. 별도 스크립트 언어, 표현식 파서, 임의 코드 실행, 두 번째 이벤트 버스를 만들지 않는다. 현재 단계 정책의 완료 집계·활성 대기열·기한 초과 정책은 정적 상태 의미이며, 이벤트 액션과 분리한다.

## 2. 저장 모델

| 모델 | 저장 내용 | 관계/불변 조건 |
|---|---|---|
| WorkflowRule | ID, 단계 ID, 이름, 활성 여부, revision, 트리거 종류, 이벤트 종류 또는 인터벌, 조건 결합 방식 | 하나의 규칙은 하나의 발동 방식만 가진다. 이벤트와 타이머를 동시에 저장하지 않는다. |
| WorkflowRuleCondition | 규칙 ID, 순서, 조건 종류, 비교 방식, 형식 검증된 값 | 지원하는 조건 목록만 허용한다. 임의 코드·SQL·재귀 표현식을 저장하지 않는다. |
| WorkflowRuleAction | ID, 규칙 ID, 순서, 액션 종류, 해당 종류의 설정, 실행 주체 참조, 선행 액션 성공 필요 여부 | 봇 참조는 bot.invoke 설정에만 존재한다. 조건·인터벌은 액션 설정에 넣지 않는다. |
| WorkflowRuleRun | 규칙 ID/revision, 이벤트 ID, 카드/보드, 단계 진입 회차, 발생자, 조건 판정, 상태·시각 | 해당 이벤트에 대한 규칙 판정의 증거다. 과거 설정을 변경하지 않는다. |
| WorkflowActionRun | 규칙 실행 ID, 액션 ID, 실행 주체, 시도 번호, 중복 방지 키, 상태·결과 참조·오류 | 전송 접수와 실행 성공을 구분한다. 기존 WorkflowEffectRun 이력은 보존하고 연결한다. |

각 액션의 설정은 기존 모델/검증기를 사용하며 알려지지 않은 키를 거부한다. 봇·컴팩터·아카이브용 테이블을 각각 규칙 엔진으로 만들지 않는다. DB ID, 공개 UID, 권한 참조는 기존 프로젝트 규칙을 따른다.

## 3. 트리거와 조건

### 트리거

- **단계 진입**: 서로 다른 단계로 이동이 커밋됐을 때 1회 발생한다. 동일 단계 내 칼럼 이동은 단계 진입이 아니다.
- **이벤트 발생**: 카드 수정·댓글 추가/수정·첨부·체크리스트 등 기존 native 이벤트를 구독한다. 기존 BotTriggerCondition 값은 호환 어댑터 입력이며 공통 이벤트 계약의 소유자가 아니다.
- **주기 도래**: 활성 상태인 해당 단계의 카드에 대해 규칙의 인터벌이 도래하면 발생한다. 타이머 이벤트 ID는 규칙·카드·진입 회차·예정 시각으로 안정적으로 결정한다. 재시도마다 새 ID를 만들지 않는다. 누락 구간은 기존 실행기의 합의된 복구 정책으로 처리하며 무제한 따라잡기를 하지 않는다.

이벤트 봉투에는 안정적인 event_id, event_type, occurred_at, actor 참조, project/card 참조, 진입 회차, 원인 이벤트/실행 참조를 둔다. 생성 시점의 원문·비밀·첨부 내용 전체를 실행 이력에 복제하지 않는다. 이벤트와 실행 예약은 원본 변경과 같은 커밋 경계에서 내구성 있게 기록하고, 외부 호출은 커밋 뒤 수행한다.

### 조건

조건은 현재 상태의 판정이며 효과 이름을 포함하지 않는다. 예: 현재 단계 일치, 단계 체류 시간, 미압축 댓글 글자 수/댓글 수/대화 턴 수, 미완료 항목 존재, 타이머·승인·의존성 상태, 발생자와 카드 작성자 차이.

첫 구현은 한 규칙 안에서 `모두 충족` 또는 `하나 이상 충족`을 지원한다. 임의 중첩 문법은 도입하지 않는다. 압축의 글자 수·댓글 수·턴 수는 사용자 합의대로 OR 조건이다. 서로 다른 의미의 조건 묶음이 필요하면 별도 규칙으로 표시하고, 액션의 필수 안전 조건은 항상 추가 AND로 평가한다. 0으로 비활성화한 압축 기준은 참으로 취급하지 않고 평가에서 제외한다. 모든 기준이 비활성인 규칙은 저장을 거부한다.

## 4. 액션

초기 액션 목록은 기존 기능으로 한정한다.

- 봇 호출: 기존 봇·Hook·카드 예약 참조를 이용한다. 규칙이 맞아도 기존 scope, 이벤트 조건, 동결 상태, 활성 상태를 다시 검사한다. 연결만으로 권한이나 Hook을 생성하지 않는다.
- 댓글 압축: 전용 컴팩터 프로필과 보드별 명시적 grant를 사용한다. 이전 요약과 새 댓글을 입력으로 삼고 원문·근거·키워드/엔티티·ACL 계약을 유지한다.
- 카드 아카이브: 현재 권한·유예·작업·승인·의존성 검사를 유지한다. 압축과 함께 설정된 기존 정책은 압축 성공이 확인돼야 아카이브할 수 있다.
- 체크항목 완료, 실행 중 타이머 정지, 작성자 알림: 기존 서비스를 호출한다.

내부에서 원자적으로 커밋해야 하는 액션은 기존 트랜잭션에서 처리한다. 외부 호출과 장기 모델 작업은 내구성 있는 예약 뒤 실행한다. 원자 처리와 외부 호출을 하나의 DB 트랜잭션으로 오래 묶지 않는다. 후속 액션은 설정된 선행 성공 계약을 따른다. 봇 요청의 accepted는 succeeded로 간주하지 않는다.

## 5. 이동 확인은 사전 조건

`자손도 함께 이동할지 확인`은 이동 후 실행할 액션이 아니다. 이동 명령의 커밋 전 확인 정책이다. 부모 없는 루트 카드·전체 자손·단계 변경 조건을 검사하고 전체 이동/단독 이동/취소를 받는다. 확인 뒤 관계·칼럼·정책 revision을 다시 검사하고 기존 원자적 이동 경로를 사용한다. 취소된 이동에는 단계 진입 이벤트와 효과 실행을 만들지 않는다.

## 6. 실행 주체·중복·재시도

- 이벤트 발생자, 규칙 설정자, 실제 실행 주체는 각각 기록한다. 저장한 사용자를 모든 효과의 자동 실행자로 간주하지 않는다.
- 압축은 컴팩터, 봇 호출은 해당 봇을 주체로 기록한다. 아카이브 등 각 액션의 주체와 보드 권한은 명시적으로 연결하고 실행 직전에 재검사한다. 내부 프로필이라는 이유로 자동 권한을 부여하지 않는다.
- 실행 직전에 카드·보드·규칙 활성 상태, 현재 revision, 단계 진입 회차, 공개 범위, 현재 실행 주체 권한과 액션 고유 조건을 재조회한다. 오래된 예약은 skipped/cancelled 사유를 남긴다.
- 중복 방지의 논리 키는 안정적인 event_id + rule_id + action_id + 단계 진입 회차다. 이 키에 unique 제약을 두고 같은 액션의 재시도는 같은 실행을 참조한다. 규칙 수정은 과거 이벤트를 새 실행으로 재생하지 않는다.
- 이벤트를 재전달해도 새 UUID로 새 실행을 만들지 않는다. 재시도 횟수·다음 시각·오류 분류를 별도 기록한다. 외부 시스템이 수신했는지 불명확한 실행은 uncertain으로 남기고 무조건 재전송하지 않는다. 외부 시스템의 멱등 키 지원 시 같은 키를 전달한다.
- 자동 액션이 만든 이벤트에는 원인 실행을 연결한다. 기본적으로 자기 규칙의 재귀 실행을 막고, 기존 봇 작성 이벤트의 루프 방지 계약을 보존한다. 일반 사용자 이벤트를 전역적으로 억제하지 않는다.

## 7. 설정 화면과 이력

사용자 용어를 `발동 시점`, `조건`, `실행할 작업`으로 통일한다. 액션을 고르기 전에 발동 시점을 설정할 수 있어야 한다. 봇/스펠별로 다른 트리거 편집기를 만들지 않는다.

예시:

1. 발동 시점: 댓글 추가 / 조건: 미압축 글자 수 12,000 이상 **또는** 새 댓글 20개 이상 / 작업: 댓글 압축(컴팩터).
2. 발동 시점: 단계 진입 / 조건: 이동자와 작성자가 다름 / 작업: 작성자 알림.
3. 발동 시점: 5분마다 / 조건: 해당 단계 체류 및 기존 아카이브 안전 조건 / 작업: 압축 → 성공 시 아카이브.
4. 발동 시점: 카드 수정 / 조건: 해당 단계에 머무는 중 / 작업: 태그봇 호출. 태그봇의 기존 이벤트 조건도 충족해야 실행한다.

이력에는 발동 시각·종류, 발생자, 대상 카드, 조건 판정, 규칙 revision, 액션별 실행자·상태·실행 시간·결과 참조를 표시한다. queued/running/accepted/succeeded/failed/skipped/cancelled/uncertain을 구분하며 재시도는 같은 실행의 시도 이력으로 제공한다. 원문 접근 권한과 비밀 마스킹을 그대로 적용한다.

## 8. 기존 데이터 전환

1. 기존 저장 필드와 실행 이력을 유지한 채 공통 규칙 모델·조회 projection을 추가한다. 이 단계에서는 구 실행 경로만 실행 권한을 갖는다.
2. entry_effects는 단계 진입 규칙의 내장 액션으로, entry_bots는 단계 진입 규칙의 bot.invoke로, policy_bots는 기존 Hook 이벤트 조건을 참조하는 이벤트 규칙으로, continuous_effects는 주기 규칙과 조건/액션으로 변환한다. 자손 이동 확인은 사전 확인 정책으로 옮긴다.
3. 기존 봇의 조건을 복사해 고정하지 않는다. 공통 이벤트 구독과 현재 Hook 조건의 교집합을 사용한다. Hook 변경/동결/삭제가 다음 실행에 반영돼야 한다.
4. 과거 설정 누락·null·명시적 빈 목록의 호환 의미를 보존한다. 읽기 변환이 설정을 자동 저장하거나 이벤트를 발생시키지 않게 한다. 구 API 저장도 공통 검증 경로를 통과시킨다.
5. 단계별 실행 소유권을 하나의 저장된 전환 상태로 관리한다. 구·신 두 실행기가 동시에 외부 효과를 실행하지 않게 한다. 비교 모드는 조건 판정만 하며 효과는 실행하지 않는다.
6. 원격 검증과 카나리 인증 E2E 뒤 공통 실행기로 전환한다. 과거 이력을 재작성하거나 기존 데이터를 삭제하지 않는다. 소유권 전환은 새 실행 예약에만 적용하며 진행 중·uncertain 실행은 원래 소유자가 처리한다. 롤백도 이 계약을 따른다.

## 9. 인수 기준

- 동일 트리거에 봇·내장 효과를 각각 연결해 동일한 조건 판정·revision·권한·이력 계약을 검증한다.
- 이벤트 생성/재전달/재시도, 동시 worker, 단계 이탈·재진입, 설정 변경·비활성화, Hook 변경, 권한 회수에서 중복 실행과 오래된 실행을 차단한다.
- 전송 접수·실제 성공·불확실 실패를 구분하고 압축 실패/진행 중/accepted 상태에서 아카이브하지 않는다.
- 기존 설정을 populated DB에서 변환하고 구 API 왕복·내역 보존·실행 소유권 전환/롤백을 검증한다.
- 실제 모델 제공자·봇 전달·보드 ACL·MCP·브라우저 설정/이력·카나리 배포를 검증한다. 소스 테스트만으로 배포 인수를 완료하지 않는다.

## 현재 근거

현재 별도 저장 경로는 WorkflowStageDefinition, 정규화는 WorkflowStageService, 내부 진입 효과는 WorkflowStagePolicyService, 봇 claim/dispatch는 WorkflowCompactionTask와 WorkflowPolicyBotTask에 존재한다. afcbbbbad의 policy_bots 구현은 호환 대상으로 보존한다. 이번 설계의 공통 규칙 모델·실행 소유권 전환은 아직 구현되지 않았다.
